# Sweep 2/3: triage reconciliation and A5 verdict replay on the 3.12 corpus

Sweep item on the corpus regenerated by #15 (`823654f`, oracle pinned to 3.12).
Branch `work/c8-sweep-triage` off `823654f`. This doc is a report: no probe,
calibration, or triage file was modified. Proposed deltas live here.

## Method

`TRIAGE.md` records 190 rows (189 fence + 1 out of scope) classified by
`probes/triage.py` from the calibration per-id outcomes, the probe JSONL,
`continuity/v1equiv.jsonl`, and the frozen v1 iteration. #15 regenerated the
probe JSONL and `v1equiv.jsonl` for the 3.12 oracle but did not regenerate
`CALIBRATION.json` or `TRIAGE.md` (both still say oracle `3.14.8`). The
reconciliation therefore re-runs the triage classifier over the new corpus
while holding the calibration per-id outcomes fixed, and diffs the result
against the committed `TRIAGE.md` row by row. The calibration is the one
input the sweep must hold constant: it is the recorded v2 score run, not a
corpus artifact.

The diff key is (bucket, rule, detail). Buckets are the four recorded
classes: probe wrong, stricter than v1, compiler gap, out of scope.

Zero unexplained rows. Every one of the 190 rows replays to the same bucket,
rule, and detail text on the new corpus. No stop-and-report.

Three independent checks back this:

1. Row diff: parsing all 190 rows out of `TRIAGE.md` and re-deriving them via
   `triage.build_report()` internals produces identical (bucket, rule, detail)
   for every id.
2. `uv run python -m benchmarks.compat2.probes.triage --check` exits 0 on this
   tree: the committed `TRIAGE.md` is byte-identical to what the generator
   derives from the new corpus (this run writes nothing in check mode).
3. Evidence-level confirmation that zero movement is the true result, not a
   classifier that stopped looking: for all 190 ids, the corpus row is
   field-for-field identical to the pre-#15 row (only the new `versions` field
   was added, and none of the 190 is in the 592 rows dropped from the corpus),
   and each row's `.v1` counterpart in `v1equiv.jsonl` likewise only gained
   `versions`. The rules read source, args, annotations, expect_exc, kind,
   category, and the v1-equiv row; none of those moved for any classified id.

So the reconciliation also explains why: #15's corpus regen moved none of the
evidence the fence rules consume. The 592 removed corpus rows are outside the
190-recorded set, and the id set of the 190 is unchanged.

## A5 verdict replay

Ran `uv run python -m benchmarks.baseline.replay_verdict` (the A5 harness
built on `benchmarks.compat2.verdict`, `skip_perf=True`; see its docstring and
`tests/compat2/test_verdict_replay.py`). Inputs are the frozen v1 numerators
in `benchmarks/compat/iterations/` and `benchmarks/compat/failed.jsonl`. No
perf run, no container: the perf gate is separate and out of scope for this
report. Exit code 0 (all four match their expected verdict).

| case | expected | replay | primary delta | census delta | area |
| --- | --- | --- | --- | --- | --- |
| kept (`046-bool-const-surface.json`) | PASS | PASS | +21.0 | 0 | none |
| dropped (`020-nan-in.json`, NaN `==` on bits) | FAIL | FAIL | +0.0 | 0 | progress (P2) |
| optional-tagged-class | FAIL | FAIL | +0.0 | 0 | progress (P2) |
| injected-wrong-output (`inject.floordiv`) | FAIL | FAIL | -1.0 | 0 | soundness:inject.floordiv (P0) |

All three historical iterations replay to their recorded keep/drop, and the
injected-bug case still trips its drop: the soundness gate fires P0 at
`inject.floordiv` (pass flips to wrong-output) with the pass-ratchet P0 right
behind it. Detail: kept moves `stdlib_surface` 1185 to 1206 (+21); both
progress FAILs are the flat-numerator shape with identical before/after
numerators; the injected case finds are exactly the two P0s the scorer
contract promises.

## Caveat for the follow-up sweep item

The replay validates the verdict machinery on the v1 numerator snapshots,
which #15 did not touch. It does not yet validate the verdict against a v2
score run on the 3.12 corpus: `CALIBRATION.json` still records the 3.14.8
calibration, so a fresh sharded calibration on 3.12 is the remaining half of
bringing `TRIAGE.md` fully onto the new oracle. Counts here say that
recalibration should reproduce the same 189/1 split unless the 3.12 runtime
itself changes an outcome. Nothing in this report proposes edits to
`TRIAGE.md`, `probes/*.jsonl`, or any frozen list.
