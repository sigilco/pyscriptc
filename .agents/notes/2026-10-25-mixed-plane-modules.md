## Q1: what "Native share caveat: 58.4% lowerable vs 18.4% planned native" means

Both numbers come from the same `pyscriptc assess --json` run over the 27 trees of the island-remainder note (`.agents/notes/2026-10-25-island-remainder.md`, summing per-file `planeMap` entries), and they measure two different questions.

- 58.4% (6,388 of 10,938 definitions) is `summary.definitions.native` of the coverage pass, computed in `coverage.py` `build_report` as `total_definitions - fenced_definitions` (`src/pyscriptc/coverage.py:625`): definitions with no fence of any kind inside their spans. It answers "how many definitions could lower natively if the planner considered each one on its own merits". It is a per-definition property and ignores the module top level entirely.
- 18.4% (2,014 of 10,938) is the plane-map share: `boxed.plane_map` per file, counting `functions[name] == "native"` (`src/pyscriptc/boxed.py:43-148`, summed in `assess.py:452-472`). It answers "how many definitions the planner actually keeps native". The difference is not noise, it is one line of code: `boxed.py:84` sets `planes[name] = ISLAND if name in fenced or top_level_island else NATIVE`. When the top level routes to the island, `top_level_island=True` and every function of the module demotes with it, whatever its own probe said.

So the gap splits exactly into the two buckets the question asks for:

- (a) Definitions that lower natively (the fence-free probe in `Lowerer._boxed_probe` would clear them, `src/pyscriptc/lower/__init__.py:889-916`) but are planned island only because their module top level is island. The top level goes island when the entry probe fences or any module-level statement is a `PS2001`/`PS2002` fence, typically one untyped or unlowered import (`src/pyscriptc/lower/__init__.py:1470-1485`, issue #627's rule). This is bucket (a) and it is 40.0 points of the 40.0-point gap: 58.4 - 18.4 = 40.0 points of demotion, i.e. 4,374 of the 10,938 definitions are lowerable-but-demoted. The per-tree evidence in #678 is the cleanest demonstration: `_pytest` has 1,146 lowerable definitions and plans 8 native because 71 of 78 files have an island top level; rich and pyasn1 have clean top levels and plan 98 to 99% native.
- (b) Definitions that truly cannot lower. These are the ones with a fence inside the definition itself: reflection (`PS1002`, routed island under the fallback tier), unsupported constructs (`PS2002`/`PS1001` inside the body), unannotated signatures. In the 27-tree population these are the 8,611 planned-island minus the demoted 4,374 = 4,237 (38.7%), plus the 313 (2.9%) unplanned (overloads, same-name methods, hyphenated module names and similar plane-map blind spots, an upper bound). The demotion cascade in `_boxed_resolve` (island-calls-native demotes the callee, `lower/__init__.py:921-940`) and the island-class cascade (#628) move a few more from (a) into (b)-looking states, but the tree-structure change of #678 would re-plan them from scratch anyway, so they stay in (b) for sizing.

### Could we lower the ~58% in 0.7.0 or 0.8.0 with little effort?

No. Keeping lowerable functions native inside a mostly-island module is a real feature with a real design cost (Q2), and it needs new machinery at three layers. What is little effort is reporting: `plane_map` already computes `demotedBy` for two demotion causes (island-class use, island-caller cascade), but the `top_level_island` branch at `boxed.py:84` records nothing per function. Writing the demotion cause into the map ("module top level is island") and surfacing it in `assess` is a day or two of work and delivers the "report the demotion cause per module" half of #678 immediately. The keep-native half is not a small patch: it needs the globals-escape analysis, the per-function plan decision and the island-side shim table of Q2, plus a per-module island namespace so a module's island seed does not collide with `__main__`'s (today the runtime has exactly one `ps_island_ns`, `src/pyscriptc/runtime/ps_island.c:1080`). My estimate: the analysis plus plan plumbing is 2 to 3 weeks for a confident subset (pure functions, no module-global reads except annotated scalar slots), then the long tail (class bodies, decorators, default-argument values) is open-ended. That is v0.8.0 work at the earliest, and only after the per-module planner (#641) gives islands an identity that is not `__main__`, because a native function in module A must survive while module B's island is running, which the single-namespace design cannot represent today. Nothing of the 40 points lands in 0.7.0 without risking the output-matching gate; the honest 0.7.0 move is the demotion-cause reporting plus #678's issue text.

## Q2: why an island top level pulls everything island, and what a mixed plane needs

### The mechanism, from the code

`_boxed_top_island` is decided once per module (`lower/__init__.py:1480`) and does three things at once. First, the entry's own fences drop with the top level (`lower/__init__.py:1637-1646`): the entry never lowers, the embedded interpreter execs the module's original source as the `__main__` body (`ps_island_top_seed`, `ps_island.c:1139-1166`), so module-level statements run once, island-side, in source order, with `__name__ == "__main__"` so main guards fire. Second, every function is removed from the native lowered list: `lowered = [record for record in lowered if record["name"] not in island]` with `island` seeded from `top_level_island` semantics through `plane_map` (`lower/__init__.py:1650`), because the island seed is the whole module source and therefore already defines every function; keeping a native copy would be dead weight, but worse, it would be a second, divergent definition of the same name. Third, all cross-function calls inside the module resolve inside the island namespace, so no seam is crossed. The design is coherent under one assumption: the island top level owns the module namespace. Every lowerable function rides along because it is simpler to sink the whole module than to share a namespace between two runtimes.

### What blocks keeping a lowerable function native in a mostly-island module

The obstacles, in the order the question lists them, with what the code does today:

- Module globals owned by the island. A native function reads its module globals from native slots (`global_slots`, `islandGlobals` in `lower/__init__.py:1175-1212`). Under an island top level the annotated scalar globals are unboxed once into shadow slots (divergence 41 documents the mechanism), so reads work. But writes are one-directional: "island-side mutation of a global is never visible to native code" (divergence 41). A native function that assigns a module global, or a `global` statement (next bullet), would silently diverge from island code reading the same name. So the keep-native rule must include "reads only island-owned globals through the shadow-slot mechanism, or no module globals at all".
- `global` statements. A `global x; x = ...` in a function is a write to the island-owned namespace. It fences today in most shapes; in a mixed module it must either fence the function island or the analyzer must prove the name is not read island-side. This is exactly the globals-escape analysis.
- Function object identity and decorators. CPython code (and any island code) that takes `mod.func` as a value gets today, under an island top level, the island copy. If `func` lowered native, `mod.func` would have to be the native callable, and #675 shows the island-to-native value seam is exactly where the plane map currently gives up (`NameError: name 'sq' is not defined` when an island function reads a native one as a value). Decorators sharpen it: the decorator expression runs island-side (the class/module body executes in the seed), so it receives the island-or-native object of the decorated function and its return value becomes the module binding. `@functools.lru_cache` over a native function must wrap it in something the island can call, i.e. the native side must expose a Python-visible shim (the `--emit binding` surface already generates exactly such shims, `binding.py:191`, used in Q3 below). User decorators that transform the function (click's `@command`) would get a native object they cannot introspect, so they must demote the function island (that is #676's rule, consistent).
- Import-time side effects. This one is already safe: CPython itself guarantees the module body runs once, at first import or as `__main__`, and the island seed runs the original source, so side effects happen exactly once island-side. The Stage 2 shape (`_boxed_stage2_source`, `lower/__init__.py:1226`) shows the reverse seam: with a native top level, the island seed re-runs only imports and literal assignments to avoid double side effects. A mixed module keeps the island-top-level choice here, so nothing new.
- Class bodies. A class body executes at import, island-side, under an island top level. A native method of an island class would need the instance layout to cross planes; #628 decided island classes pull in compiled functions that name them, the reverse (island class with native methods) needs native methods as Python-visible shims with boxed self, which the binding surface gives for free functions but not for methods on island-built classes. First cut: a mixed-plane module keeps classes island unless the whole class probes clean.
- Default arguments evaluated at import. `def f(x=TIMEOUT)` evaluates `TIMEOUT` island-side at seed time; the value is baked into the island copy. If `f` lowers native, defaults must be constants the native table can replay (`self.constants`), or the island value must be unboxed into the slot table the way annotated globals are. The analyzer can reuse `_boxed_is_literal_module_value` for exactly this check.
- Monkeypatching. If island code does `mod.func = other`, a native direct-call site never sees the patch. mypyc accepts this (documented divergence, "compiled code generally doesn't use this namespace"), numba does not have the problem because dispatchers are Python objects. pyscriptc must either fence modules that rebind their own lowerable functions after definition (detectable in the analyzer as an `ast.Assign` to a function name at module or function level) or accept the same documented divergence mypyc has. Fencing the writer is the honest first version.
- The native/island seams. Two directions exist. Island calls native: needs the shim table (a real Python function object per native function, exposed in the island namespace, backed by the existing `ps_island_fn_invoke` trampoline machinery, `boxed.py:34`); this is the same shape as the generated binding modules, so the runtime plumbing exists. Native calls island: already exists (the trampoline `lower/__init__.py:411` routes calls to `island_fns` through the island). Value crossings both ways are the hard part (#675 native function as a value, #674 list copy-back), and a mixed module strictly increases how often they fire. The safest rule, and the one the corpus evidence supports: keep native only functions whose transitive callees are all native and whose non-local reads are parameters, builtins, typed constants and shadow-slot globals.

### Safe-to-keep-native detection

A function is keep-native when all of these hold, each mechanically checkable on the AST before bodies lower:

1. its own `_boxed_probe` clears (no fences inside), i.e. it is in the 58.4%;
2. it reads no module global except (a) names in `self.constants` (typed constants, already replayed natively) and (b) names with an active annotated scalar slot (`global_slots` with `island=True`, the divergence-41 mechanism); it writes no module global and contains no `global` statement;
3. it calls only other keep-native functions (the fixpoint loop already implemented in `_boxed_resolve`, `lower/__init__.py:921-940`, with the direction reversed: today it cascades island callers to native callees; mixed-plane needs the symmetric rule that a native function may only call natives);
4. it is not used as a value by island code in ways that need the island copy, and is not decorated by anything except the closed decorator set (`@staticmethod`, `@classmethod` shapes the lowerer already accepts; everything else demotes, per #676);
5. its default arguments are literals or names satisfying rule 2;
6. no module-level statement rebinds the function's name after definition (monkeypatch check, one walk of `tree.body`).

Detection is inherently a transitive, fixpoint analysis over per-function ASTs with module-scope escape rules; that is more compiler complexity than today's per-definition probe (which is already a transitive cascade, so the machinery shape exists), and it is the main reason this is not a two-line change to `boxed.py:84`.

### Components needed

- Globals-escape analysis: per function, the set of module-global reads/writes, classified against `constants` and `global_slots`; produces the keep-native predicate of rule 2 plus the monkeypatch fence of rule 6. Reuses `definition_spans`/walk helpers in `boxed.py`.
- Per-function plan decision: replace the `top_level_island` blanket at `boxed.py:84` with the six rules above, keeping `demotedBy` populated with causes. The natural home is `Lowerer._boxed_resolve` (it already owns the probe, the cascades and `demoted_by`), not the per-module planner: `package.py`'s `_program_plan` works at unit granularity and knows nothing about function bodies. #641's per-module planner is a prerequisite in one specific sense only: its runtime half (one namespace per module, cross-module trampolines) is what a mixed module's island seed must become, because today `ps_island_top_seed` execs into the single `__main__`-shaped `ps_island_ns`. So: plan decision in the lowerer, namespace work rides #641.
- Native shim table callable from the island: one Python object per keep-native function, registered into the module's island namespace at seed time, backed by `ps_island_fn_invoke` with the arg-marshalling the trampoline already has. The generated binding module (`binding.py:291-444`) is a working reference implementation of the same seam; the difference is the shim table is built into the binary instead of a `.so` next to it.
- Uncertainty, flagged rather than guessed: the runtime cost of routing a native call from island code through a shim per call site (the Q3 fork-context pool over the binding worked, but per-call overhead was not measured); whether `_boxed_probe` is sound as a keep-native predicate when module globals it reads are island-owned (the probe lowers against the native slot table, which is right for constants and wrong for values the island mutates); and whether the island seed can carry `import` statements for modules the native side lowered (a shared import would double-import, which CPython caches, so probably fine, unverified).

### Comparison with numba, Cython pure mode and mypyc

- numba `@jit` never executes the module top level: the module always runs under CPython and `@jit` swaps in a `Dispatcher` object, a regular Python callable, per function (numba docs, `Dispatcher.py_func` keeps the pure-Python function). Mixed planes are trivial for numba because its compiled artifact is itself a Python object; there is no separate process plane. pyscriptc's native plane is not a Python object, which is why it needs the shim table where numba needs nothing. (Sources: numba readthedocs jit page; `numba/core/dispatcher.py`; the object-mode fallback was deprecated in 0.59, issue #3907.)
- Cython pure mode is the same trick at module granularity: the module runs as CPython byte code, `cdef`/`@cython.cfunc` functions get C fast paths inside, and `def` functions remain Python callables. The top level is always CPython. Cython's `cpdef` is the closest analog to pyscriptc's mixed plane: one function, two entry points (C signature plus Python wrapper), and Cython generates both automatically. The wrapper is the shim table, generated per function, and Cython proves the demand for it.
- mypyc is the honest precedent for pyscriptc's shape: whole modules compile to C extensions, compiled code early-binds calls and does not go through the module namespace, and the documented cost is exactly the list Q2 names, minus islands: no `__name__ == "__main__"` in compiled modules, no monkeypatching of compiled functions, late binding only for non-final module globals, and compiled modules keep a regular namespace dict pointing at wrapper functions so interpreted (or in our terms island) code can call in (mypyc wiki, "Calls to other compiled functions don't go through the Python module namespace"; `differences_from_python.html`). mypyc never splits a module; a compilation unit is all-compiled or all-interpreted. That is evidence that even a mature, CPython-adjacent implementation chose not to solve intra-module mixed planes, and took the per-unit (module) granularity pyscriptc's #641 planner is heading toward.

## Q3: multiprocessing probes (Linux runs, macOS static)

Host macOS could not run any probe end to end: the machine's POSIX semaphore pool is exhausted (`kern.posix.sem.max` = 10,000, leaked across the 7-day boot; `mp.Lock()` fails with `OSError: [Errno 28] No space left on device` under plain CPython 3.14.9, verified with a 20-line C `sem_open` repro and a Python repro, `fork`+`os.pipe` still works). Per the owner's instruction the runtime behavior below is Linux-in-Dory, labeled (Linux); macOS behavior is static analysis of the same binaries plus the source, labeled (macOS static). CPython baselines are the container's 3.14.8 oracle plus 3.14.9 where the binary links it.

Probe sources (in `/tmp/oc/mp/`, copied to the worktree for the mount): `mp_pool.py` (Pool.map over a typed worker, main guard), `mp_process_queue.py` (Process + Queue), `mp_ppe.py` (ProcessPoolExecutor), `mp_noguard.py` (Pool at module top level, no guard), `mp_semprobe.py` (sem mode = Pool, forkpipe mode = fork + os.pipe, argv-selected), `mp_spawnfork.py` (Process under fork/forkserver/spawn contexts), `mp_main_import.py` (`__name__`, argv, nested import of `multiprocessing.spawn`), `mp_pickle_fn.py` (`pickle.dumps` of a module-level function then Pool).

### What the compiler does with each (Linux and macOS, same planner)

`multiprocessing` and `concurrent.futures` are not in the closed import table, so without the fallback every probe refuses at exit 3 with `PS2002: multiprocessing is not in the closed import table` plus per-use fences (`mp is not a local or parameter`, `call to ProcessPoolExecutor is not lowered`, and in `mp_semprobe.py` also `PS2001: os.pipe is not in the lowered subset of os`). With `--fallback=cpython`:

| Probe | moduleTopLevel | Functions (plane map) |
|---|---|---|
| `mp_pool.py` | native | `worker: native`, `main: island` |
| `mp_process_queue.py` | native | `producer: island`, `main: island` |
| `mp_ppe.py` | native | `double: native`, `main: island` |
| `mp_noguard.py` | island | `worker: island` (demoted with the top level) |
| `mp_semprobe.py` | island | both inner functions island |
| `mp_spawnfork.py` | native | `_child: native`, `show/main: island` |
| `mp_main_import.py` | native | `task: native`, `main: island` |
| `mp_pickle_fn.py` | native | `worker: native`, `main: island` |

The `main: island` in the guarded scripts is the fence of the `import multiprocessing` statement landing in the synthesized entry (issue #627's import fence rule), which is exactly #678's demotion pattern in miniature: `worker` in `mp_pool.py` probes clean and lowers, `double` and `task` likewise, and they stay native even though the top level's import is what fenced, because the *entry* fences rather than the top level going island. `mp_noguard.py` shows the other path: unguarded `mp.Pool(2)` fences the entry probe, the whole top level goes island, and the lowerable `worker` demotes with it.

### Runtime results (Linux, container CPython 3.14.8/3.14.9 oracles)

| Case | CPython (Linux) | `--fallback` binary (Linux) |
|---|---|---|

| `mp_pickle_fn.py` | `pickled ok, bytes: 34` then pool | `NameError: name 'worker' is not defined` exit 1 (fails before pickling) |

The 141 is one root cause, not five: `strace -f` on the binary shows `mp.Pool` asking `sys.executable` to spawn the resource tracker, and the binary's island reports `sys.executable == ''` (probed with a dedicated script), so CPython execs `""` with `["", "-c", "from multiprocessing.resource_tr..."]`, the exec fails ENOENT, the tracker pipe closes, and the parent's `REGISTER:` write dies on SIGPIPE (`write(6, "REGISTER:/mp-...:semaphore\n") = -1 EPIPE`). The native runtime does not install a SIGPIPE handler, so the process dies with 141. Note `sys.argv` inside the island is right (`./mp_exe` printed `['./mp_exe']`); only `sys.executable` is empty, because `Py_InitializeEx(0)` without config gives no executable path (`ps_island.c:37`).

### What breaks at runtime, and why (Linux)

1. `sys.executable` is empty in the embedded interpreter. Every `multiprocessing` path that spawns a helper (resource tracker for semaphores, forkserver) execs `sys.executable`. Fix candidate: set `sys.executable` from the runtime at island init if empty. Demonstrated sufficient for the tracker: after a one-line `sys.executable = "/opt/python/.../python3.14"` shim, the tracker spawns (strace shows the real interpreter exec'd).
2. Pickling island functions fails: `Can't pickle <function worker ...>: it's not found as __main__.worker` (guard-shaped scripts) or `No module named '__pyscriptc_island__'` (island top level). Two sub-causes: the function's `__module__` is `__pyscriptc_island__` (or the seed's namespace is not registered as a module in `sys.modules` at all: probed, `sys.modules["__main__"]` is an empty BuiltinImporter module that does not contain `worker`, while the seed's own `__name__` reads `__pyscriptc_island__`), and there is no importable module to re-import from. Fix candidates, both demonstrated: register the seed namespace as a module object in `sys.modules` (the `__pyscriptc_island__` name would then pickle-resolve), or rewrite `__module__` to a registered name at seed time. With `producer.__module__ = "__main__"` plus registering `producer` on `sys.modules["__main__"]`, the Process+Queue probe printed `[0, 10, 20]`, byte-identical to CPython.
3. Spawn/forkserver re-import `__main__` from disk. The spawn child runs `python -c "from multiprocessing.spawn import ..."` and reads `main_path`, which the binary records as the original source path (strace: the child `openat`s the `.py` file). In a directory that still has the sources the file exists (the probes pass with shims), but a shipped binary alone cannot spawn children: `FileNotFoundError: .../mp_q4.py` when run from a directory without sources, then `OSError 104` in the parent. The fork context has none of this: the fork-context Pool over a compiled (binding) worker printed `[10, 12, 14]` with only the binary and `libbindmod.so` present, no sources.
4. Fork safety of the embedded interpreter: positive result. A fork-context Process whose target runs island code (importing `json` inside the child) works: `got: {"island": "ok", ...}`, and the island stays alive in the parent after the fork. One caveat observed, matching the known island-module-identity problem #679: an `atexit.register` inside a forked island child does not fire (CPython does fire it), because `bootstrap` runs `runpy`-free inside a namespace whose interpreter teardown never happens, the same root cause as #679's missing atexit.
5. Compiled (native) functions as pool workers need the value seam. A native `worker` with island `main` fails with `NameError: name 'worker' is not defined` (island main cannot even read the name, the #675 class of seam). The working pattern is `--emit binding`: compile the worker module to `bindmod_binding` + `libbindmod.so`, then `import bindmod_binding` inside island code, patch `f.__module__ = "__main__"`, register it on `sys.modules["__main__"]`, and Pool.map over it under the fork context prints `[10, 12, 14]`. Spawn with the same shim still fails: the child re-imports `__main__` from the source file and gets `AttributeError: module '__mp_main__' has no attribute 'double'` (the child runs the `.py`, which has no `double` because that module never defined it; the binding lib is not on the child's path either). So fork+binding is the only end-to-end compiled-worker path today.
6. Re-executing the binary: children never execute the pyscriptc binary. Spawn/forkserver children exec `sys.executable` (a CPython interpreter, once it is set) and re-import the `__main__` *source*. The binary is re-executed by nothing; the SIGPIPE-141 comes from the failed tracker exec, not from re-running the binary. A "children run the binary" design is not what CPython's multiprocessing wants; the shims must instead make the source files (or an equivalent importable artifact) available next to the binary.

### macOS static (no runs possible)

The macOS binaries are the same planner output (the table above is platform-independent; the mac `mp_pool` binary embeds `libpython3.14.dylib` from the uv interpreter, verified with `otool -L`, and references `_Py_InitializeEx`, `nm`), so the compile-time behavior is identical. At runtime macOS differs in three ways, from the code: default start method is `spawn` on darwin (CPython 3.14's `context._force_start_method`), so every Pool immediately needs `sys.executable` (the empty-string exec, SIGPIPE 141, same failure class as Linux but hit at Pool creation rather than forkserver setup); posix named semaphores exist (`/mp-...` names, created via `sem_open`), and the host's pool exhaustion is an environment defect, not a compiler one; and `os.fork`+pipe (the `forkpipe` mode) is fork-safe the same way, so that probe's binary would match CPython as it does on Linux.

### Smallest issue set that makes the common patterns work

- New issue (v0.7.0): island `sys.executable` is empty. One `PySys_SetObject` at init from the runtime's own interpreter path; unblocks the resource tracker, removes the 141 exit, and is testable with a two-line probe. This is the single highest-leverage fix; without it nothing else can be observed.
- New issue (v0.7.0): register the island seed namespace as a module in `sys.modules` (name `__pyscriptc_island__` or a per-module name after #641) and set it as `__main__`'s dict contents so `pickle` and `multiprocessing` can resolve island functions; include the `__main__` registration of seed-defined functions the way CPython's `runpy` does. Demonstrated sufficient for Process+Queue end to end.
- New issue (v0.8.0, rides #641): give the binary a story for spawn/forkserver's `main_path` re-import: embed the sources (the program-wide island already embeds them, `boxed.py:300-324`) and register a finder so the spawned child of *CPython* (not the binary) can import them, or document fork-only. Without it, spawned children need the source tree on disk.
- Existing #679 (v0.8.0): island module identity (`__name__`, atexit, pickle) is the same root cause as item 2; merge the note's evidence into it when filing.

Linux container (representative; `cd /work/.agents/tmp-mpprobes` inside the image, worktree mounted):

```
docker build -t pyscriptc-dev docker/                       # once
docker run --rm -v "$HOME/.worktrees/pyscriptc-mixplane:/work" \
  -v pyscriptc-venv:/opt/venv -v pyscriptc-py:/opt/python pyscriptc-dev \
  bash -c 'cd /work/.agents/tmp-mpprobes && uv run pyscriptc compile mp_pool.py --fallback=cpython --emit bin && ./mp_pool; echo exit=$?'
# mp_pool: exit=141 (SIGPIPE after execve("", ["", "-c", "from multiprocessing.resource_tr..."])) 
docker run ... pyscriptc-dev bash -c 'cd /work/.agents/tmp-mpprobes && \
  /opt/python/cpython-3.14.8-linux-aarch64-gnu/bin/python3.14 mp_pool.py'
# [1, 4, 9, 16], exit 0
```
