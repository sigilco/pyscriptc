## 2. Lane split: what the census can and cannot see

All 4041 fences are shared-frontend fences: `coverage.build_report` runs `lower_file`/`lower_directory` only, so every fence is raised by `lower/` (PS1xxx annotation and type fences concentrated in `lower/_annotations.py`, `lower/_expr.py`, `lower/_stdlib.py`; PS2xxx name and construct fences spread across `_stmt_*`, `_calls*`, `_call_attr`, `_classes*`, `_closures`, `_misc_emit`, `_module_driver`) or by the coro pass. There is no such thing in this census as a direct-emitter-only fence, because the direct emitter never runs and never fences; emit-side rejection today is the MIR slice predicate, which is a different mechanism (`mirlower.supported_*` plus `emit/_mir_in.py` telemetry) and produces no census entries. Conversely every census fence is unreachable from the MIR lane in the strict sense: a fenced function produces no lowered body, so neither `emit/llvm` nor `mirlower.lower_module` ever sees it. The honest three-way split is therefore: (a) 4041 shared-frontend fences that block both lanes, (b) zero emitter-only fences measurable here, and (c) the MIR out-of-slice set, which is not a fence count at all but a separate coverage metric measured below.

The MIR-lane self-host measurement, run as `lower_directory(src/pyscriptc)` then `mirlower.lower_module(module)`: 518 module-level functions lowered to dict IR, of which the MIR slice admits 80 and skips 438. So the MIR lane's self-host fence-equivalent today is 438 skipped functions plus all 4041 lower fences stacked in front of them; corpus-side the picture is different because `scripts/mir_coverage.py` now reports 33 of 33 non-fenced visible-corpus functions in slice, 100 percent, after the list/dict/try/class merges #1015-#1037 and the direct-lowerer unfences landed (the 2026-11-06 gap map and the flip plan's 32-of-33 figures are stale).

## 3. The key design question: lifting a fence only for the new architecture

Today there is exactly one lowering output: `lower_source`/`lower_file` return a `dict[str, Any]` module; the typed `_irnode` records are built transiently inside `lower/` and immediately flattened by `node_to_dict`, and `mirlower.lower_module` consumes that same dict module. A `lower/` fence therefore cannot be "lifted for MIR only" at the fence site, because MIR cannot consume anything the dict IR cannot represent until `mirlower` reads typed HIR, which is future work already scheduled (the dict-IR deletion map requires `lower/` to stop returning dicts before v0.10.0). Option (a), a `PYSC_MIR`/HIR-only flag threaded through `lower/`, is premature and wrong-layered: it would double every fence predicate, it would have to be added at hundreds of `fail` sites, and it buys nothing until the MIR lane has a typed input, at which point the flag is deleted anyway. Option (b), moving the check to the old-lane adapter, is closer to the real architecture but should not be implemented as a per-site move either; the correct form is the already-planned inversion: `lower/` emits typed module records, `node_to_dict` becomes a compat shim used only when the old lane must emit a function, and fences that check "is a lowered type in the IR" (PS1106 unlowered-type-name, PS1104 dynamic-annotation, the type halves of PS1003/PS1101/PS1103) are re-pointed at the typed `T` vocabulary in `_irnode.py` instead of the dict vocabulary. Constructs typed HIR can carry but dict IR cannot (an `Any`/unknown leaf, foreign class types like `ast.expr`, real unions and generic aliases) then lower cleanly, reach MIR, and are fenced only at the dict boundary when `PYSC_MIR=0` asks the old lane to emit them, which is exactly the honest behavior for an escape hatch that dies in v0.10.0.

Cost comparison: option (a) costs a flag plus branch at every fence site across 23 `lower/` files, collides with every in-flight unfence PR, and is throwaway work the owner explicitly forbade (it exists only to serve the old lane's continued existence). Option (b) costs the typed-module-record work that v0.10.0 needs anyway (deletion-map precondition 1), plus `T` vocabulary extensions in `_irnode.py`/`tirserde.py`, and it deletes fences rather than relocating them. Recommendation: adopt (b) sequenced as typed module output first, vocabulary second, fence re-pointing third; do not add lane conditionals inside `lower/` fence sites. Against the v0.10.0 deletion this is strictly cheaper because every line spent on (a) is deleted with the old lane.

On the metric: the 4041 baseline contains zero MIR-lane information, and `census_pins.json` cannot express it because it counts lower/ fences per module only. Proposed metric, `mir_selfhost`: run the census lowering once, then `mirlower.lower_module`, and report `{lowered, skipped, skipReasons}` where skip reasons reuse the `mir_coverage.py --all-reasons` vocabulary; self-host baseline measured today is 80 lowered / 438 skipped of 518. Implementation path: add a `--mir` section to `benchmarks/compat2/census_self.py` (it already has the lowered module in hand via `build_report`'s `_lower`, so the extra cost is one `lower_module` pass, measured at roughly the same order as the census itself) or a sibling `census_mir.py` if the runtime proves annoying; either way it is a reported figure in the iteration report, tracked like `mise run boxed:cost`, not a gate. `tests/census_pins.json` stays the shared-frontend ceiling and keeps being regenerated only by `scripts/repin_census.py`; it is not a frozen gate file, so repins are legal, but this plan edits neither it nor any frozen hash file. A MIR skip-count pin should wait until the slice is stable enough that the number moves monotonically; pinning 438 today would just recreate the census_pins merge pain on a noisier metric.

## 5. User-visible versus self-host-visible

Every census fence is self-host evidence: the census compiles `src/pyscriptc`, so batches B1-B7 measure the compiler compiling itself and their end-user value is indirect (a self-hosted compiler is the v0.10.0+ goal, not a user feature). End-user fence evidence must come from the visible corpus and the support ledger only: `scripts/mir_coverage.py` reports 33 of 33 non-fenced visible-corpus functions in the MIR slice today, and `data/compat/support.json` is the support-state receipt (generated summary: builtins 25 green, 22 yellow, 23 red; stdlib 0 green, 61 yellow; packages 2 green, 7 yellow, 9 red). The genuinely user-visible fence-clearing work is the MIR slice expansion already landed plus what remains: M-4 closures and callable values (`.agents/notes/2026-11-06-mir-closures-env-cells.md`, the 2026-10-17 backlog's roughly 40 percent callable-construct estimate covering `map`/`filter`/`iter`/genexprs/method values), the R-2 typed coro port for `yield` (`.agents/notes/2026-11-06-typed-coro-generator-lowering.md`), union types and multi-arm optionals (47 census fences plus the PS1101/PS1102 checker fences that also appear in user code), and the direct-lowerer unfence pattern proven by `advance`/`shift`/`sieve`/`check`. Recommendation: weight v0.9.0 release-note value on the user-visible MIR batches and report the self-host census delta as the v0.10.0 receipt material it is; do not let self-host fence batches crowd out M-4 or R-2, and never quote a census delta as user-visible compat gain.

## 7. Risks and open questions (recommended defaults)

1. 2000 may not be reachable before v0.10.0 without the deletion dividends; default: treat 2000 as the drop-boundary target, report the cumulative curve at each iteration boundary, and let B8 count only when the modules actually delete.
2. The typed-vocabulary batch may clear annotation fences while bodies keep fencing, netting far less than 774; default: land the `Any` leaf alone first (T3) and let the measured delta decide whether foreign `ast.*` types are worth the `T` surface.
3. The 69 `ast`-table fences probably should not clear at all; default: keep `ast` fenced, treat self-hosted-AST as an island or stdlib-surface decision owned elsewhere.
4. Name-resolution unfences could mask real scoping bugs; default: every unfence PR carries a runtime or oracle check on the touched path, not just a census delta.
5. The real v0.10.0 gate is the MIR self-host slice (80 of 518 functions today), which is orthogonal to census fences; default: track `mir_skipped` as a reported metric beside the census and do not let fence batches starve M-4/R-2.
6. Family-to-batch estimates are inferred from message sampling, not per-fence lane analysis; default: re-run the per-file/per-message breakdown at each batch boundary before committing to a target date, and keep `census_pins.json` repins the only pin mechanism.
