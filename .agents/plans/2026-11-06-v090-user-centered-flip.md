# v0.9.0 user-centered flip: typed HIR + MIR as the default

Date: 2026-11-06. Epic: #817. Milestone: v0.9.0. Docs only; no code changes and no frozen-file edits. Owner direction recorded here: do not target 100 percent compat with the old dict-IR plus direct-emitter architecture when that means porting inefficient, duplicated or overhead code; the flip gate is user-centered (fences lowered, user-visible gains), not slice parity. This plan also answers the merge-conflict cost of parallel MIR work, which has been very high.

## 1. Old-lane inventory: what not to port, what must port

Measured on this branch (`work/plan-flip` at `3c09d2e4`): the MIR lane is `mir.py` 1100, `mirlower.py` 2710, `miremit.py` 1960, `mirverify.py` 739, `mirprint.py` 325 and `emit/_mir_in.py` 245 lines, 7079 total (`wc -l`). The old lane it replaces for covered functions is `emit/llvm/` at 6087 lines across 12 files plus the `emit/_ir.py` dict-accessor seam at 930 lines (`find ... | xargs wc -l`; the whole `emit/` package is 7310). `lower/` is 17285 lines across 23 files and is shared by both lanes today.

Worth NOT porting, with evidence. (a) The byte-identity machinery that exists only to reproduce the direct emitter's incidental shape: `MirBlock.hint` and `MirBlock.label_id` in `mir.py` (lines 492-503) record the direct path's lazily allocated label numbers so the MIR lane can print identical `.ll` text; `tests/test_mir_hashseed.py` pins output against `PYTHONHASHSEED` variation that was a dict-iteration artifact, not semantics. (b) The out-of-band side channels: `MirFunction.helpers` (mir.py lines 566-571) smuggles `ps_*` helper spellings past the instruction stream, `call_args` and `callees` are dicts keyed by instruction index because the four-int instruction has no room, and `fn.helpers` is deliberately omitted from `serialize()` so the digest cannot see the spelling. (c) The hand-numbered op ids with gaps and jumbled order (`MIR_ANDW = 29` before `MIR_NEWSEQ = 30..34`, `MIR_ORW`/`MIR_XORW` at 35-36 after the sequence block, class ops 37-39, `MIR_MAP_PUT = 40`, try ops 41-52, `MIR_INITCALL = 53`): the "append above the highest id" convention is already the de facto rule every parallel session follows, and it is the collision point. (d) The literal table duplication documented in section 4. (e) Any remaining dict-IR reads inside the new lane: `mirlower.lower_module` still consumes `Dict[str, Any]` modules and `emit/_mir_in.py` re-walks the same dict nodes the slice predicates reject, so today the dict IR is traversed twice per compile (once by `emit/llvm`, once by `mirlower`); the typed-HIR input removes this rather than porting it.

Must port, because it is semantics or shared surface: the runtime C helpers both lanes emit calls to (`ps_seq_*`, `ps_map_*`, `ps_str_*`, `ps_try_call`, the `EXCEPTIONS` code table), the module-scope text the #937 decision already ruled shared (runtime header, ABI declarations, helper bodies, entry point), the slice-predicate semantics in `mirlower.supported_*` and `emit/_mir_in`, the per-function fallback telemetry (B11), and the `PYSC_MIR` escape-hatch contract pinned by `tests/test_mir_escape_hatch.py`.

## 2. User-visible gains the new architecture unlocks

`scripts/mir_coverage.py` measured today reports 32 of 33 non-fenced functions in slice, 97 percent, over the 20 visible corpus scripts (the script's docstring states it only tests functions that are not already fenced, so this measures slice breadth, not total coverage; an earlier same-day note `.agents/notes/2026-11-06-mir-coverage-gap-map.md` recorded 3 of 31 before the str, list/dict, try and class merges #1015-#1035 landed). The remaining corpus blockers named there are recursion policy, `binary_trees` class shapes, and direct-lowerer unfences (`shift`, `sieve`, `advance`, `check`), which are `lower/` work, not MIR work.

The design notes in `.agents/notes/` size the next families: M-4 closures and env cells (`2026-11-06-mir-closures-env-cells.md`, not landed), M-2 list/dict value types (`2026-11-06-mir-list-dict-value-types.md`, `MIR_P` tag already in `mir.py` line 63), M-3 try handlers CFG (`2026-11-06-mir-try-handlers-cfg.md`, landed as #1030), M-1 str value type (landed #1015/#1022), and R-2 typed coro (`2026-11-06-typed-coro-generator-lowering.md`; `coro.py` is 2222 lines of dict-IR-to-dict-IR resumable pass per `.agents/notes/2026-11-06-dict-ir-deletion-map.md`).

Census fence families, measured today by `uv run python -m benchmarks.compat2.census_self --json /tmp/census-self.json` over `src/pyscriptc` (4039 fences, 131 modules, 1476 of 2733 definitions fenced, 67777 lines; `tests/census_pins.json` holds the same 4039 as per-module ceilings). The ranking's `families` counts and package reach: name-resolution 985 fences in 63 packages, construct-other 639 in 63, unlowered-type-name 432 in 46, dynamic-annotation 342 in 76, local-inference 303 in 34, field-lookup 244 in 21, unlowered-call 240 in 50, call-arity 107 in 24, type-mismatch 96 in 37, import-table 85 in 74, union-types 47 in 20, generic-alias 25 in 7, class-body 6 in 5, keyword-args 19 in 11. Inference, marked as such: the families that become tractable only through the typed HIR plus MIR path, ranked by fences cleared per effort, are (1) closures and callable values, which the 2026-10-17 backlog estimates unblock roughly 40 percent of its fenced construct list (`map`/`filter`/`iter`/genexprs/method values all need a first-class callable) and which M-4 already decomposes into env-cell ops, effort L; (2) generators and `yield`, which need the typed coro port (R-2) because `coro.py` today is a dict-IR pass, effort XL but it is also the single largest dict-IR deletion (2222 lines); (3) union types and multi-arm optionals (47 census fences plus the PS1101/PS1102 checker fences), effort M, mostly HIR/checker work with little MIR surface; (4) generic aliases and class-body constructs (25 and 6 census fences), effort M, HIR-side. The big census families (name-resolution, construct-other, dynamic-annotation, unlowered-type-name, local-inference) are self-host compile fences: clearing them is what lets the compiler compile itself through the new path, which is the v0.10.0+ goal, not the v0.9.0 flip gate.

## 3. User-centered flip gate proposal (replaces the 80 percent slice-parity bar)

Current bar, from the unsigned draft in PR #937 (`.agents/plans/decisions/2026-11-05-mir-contract-amendment-and-layered-gate.md`, fetched via `gh pr diff 937`): at least 80 percent of non-fenced corpus functions lower to MIR, kill criteria under 60 percent at scope check or an unreliable A/B harness, plus the layered gate (per-function byte identity through v0.9.0, runtime A/B differential as release gate, whole-module byte equality retired). The operational checklist is `.agents/docs/release/mir-flip-checklist.md`.

Proposal: keep every existing measurement, change which ones gate. Reported figures, not gates: slice coverage from `uv run python scripts/mir_coverage.py --json` (80 percent stays the aspiration printed in release notes; under 60 percent still moves the flip to v0.10.0 per the existing kill rule). Gates, all measured by existing scripts: (1) runtime differential clean: `uv run python scripts/runtime_ab.py` reports 0 FAIL and 0 ERROR over the mir_leaf fixtures plus every visible corpus script that has an in-slice function, extended per the FR-2 note in the checklist so all in-slice corpus functions join the default set; (2) scorer parity: `uv run python scripts/compat_mir_flip.py` reports 0 outcome flips in both directions on the visible corpus (it already runs `--no-cache` per lane and refuses the holdout); (3) perf: `uv run python scripts/mir_perf_ratio.py` ratio within the bootstrap 95 percent interval of 1.0 on every workload, and `mise run bench:baseline` (`uv run python -m benchmarks.baseline.run --check`) green; (4) census non-regression: `uv run python scripts/repin_census.py` produces no pin increase and `data/benchmarks/census-self.json` fence total does not rise; (5) byte identity: `uv run pytest tests/test_mir_leaf.py tests/test_mir_hashseed.py -q` stays green through v0.9.0 per the layered gate, and `tests/test_mir_escape_hatch.py` is inverted in the same commit that sets `MIR_DEFAULT = True` in `src/pyscriptc/miremit.py` (line 133 today). User-visible gain evidence for the release receipt: the census delta and the fence families landed (section 2), plus the compat site numbers from `data/compat/support.json` regenerated by `scripts/gen_support_table.py`, which must show no status regression.

Draft amendment text for #937 (owner signs; this replaces the flip-bar paragraph and adds the gate table): "Amendment to `2026-11-02-mir-backend-only-contract.md`, second revision. MIR is the backend contract for every function the MIR slice covers, and the typed-HIR fallback remains a bounded measured exception whose share is reported as slice coverage. The v0.9.0 flip bar is user-centered, not slice-parity: the flip requires a clean runtime A/B differential over all in-slice visible corpus functions, zero scorer outcome flips in both directions on the visible corpus, perf baseline and MIR/direct ratio within noise, no census or support-ledger regression, and per-function byte identity through v0.9.0. Slice coverage of 80 percent is the reported aspiration; under 60 percent at the scope check still moves the flip to v0.10.0, and the typed-HIR fallback share still reaches zero at the v0.10.0 drop. Whole-module byte equality stays retired."

## 4. Conflict-reduction architecture

Measured collision surface, inference flagged: `git log` on the last 100 commits touching MIR or hotspot paths (`src/pyscriptc/mir*.py`, `emit/_mir_in.py`, `tests/test_mir*`, `tests/census_pins.json`, `data/compat/support.json`, `benchmarks/compat2/probes/IR_HASHES.json`) shows `tests/census_pins.json` touched by 68 commits, `tests/test_mir_leaf.py` by 22, `data/compat/support.json` by 3, `IR_HASHES.json` by 0, and 22 commits touched two or more of the five op files with 11 touching four or more. Squash merges do not record conflicts, so co-touch is the measurable proxy for collision probability, not a conflict count.

Root cause, with file evidence: the self-host compiler's closed import table means a module-level table in `mir.py` binds a global slot that does not ride the package export table, so consumers cannot import `OP_ARITY`, `OP_RESULT_TYPE`, `TERMINATORS` or `VALUE_OPS`. The result is literal duplication: `mirverify.py` lines 65-135 re-spell `_OP_ARITY` as a 53-entry int-literal dict plus `_EXTRA_TERMINATORS = [50, 51, 52]` and `_TAGLESS_VALUE_OPS = [41, 43, 46, 48, 49]`; `miremit.py` lines 171-234 onward re-spell `_MIR_TERMINATORS`, `_OP_ARITY` and `_OP_RESULT_TYPE` over imported constants; `mirprint.py` keeps `OP_NAMES` (line 87) and `_TERMINATORS` (line 144); `mirlower.py` keeps its own `_EXPR_KINDS`/`_STMT_KINDS`/`_BUILTIN_CALLS`/`_MODULE_CALLS` predicate tables (lines 301-836) and per-kind `MirLowerError` dispatch. Every new op therefore needs literal edits in five files, and drift is caught only by tests (`mirverify.py` line 69 comment: "a drift is a test failure, not a silent wrong verification"). The same self-host spell constraint is documented in `pyproject.toml` per-file-ignores (the `Dict[str, Any]` spelling is deliberate because lowercase `dict[str, Any]` fences PS1106 in the census lowerer).

Staged design, cheapest first. Stage A, single-source op spec: the blocker is that tables do not cross modules, but functions and classes do (`copy_result_type`, `MirFunction` are imported fine). Replace the four module-level tables in `mir.py` with importable function accessors (`def op_arity(op: int) -> int`, `def op_result_type`, `def is_terminator`, `def is_value_op`) spelled as if-chains over the op constants, which `mir.py` already proves self-host can lower (it has 0 census fences). Consumers then call the functions; the duplicated tables in `mirverify.py` and `miremit.py` are deleted. If the spike shows function calls in hot verifier/emitter loops cost too much, the fallback is a committed generated file produced by a `scripts/gen_mir_ops.py` from one spec plus a drift test, the same pattern as `scripts/gen_case_tables.py`. Either way the spec is one file and per-file tables become derived or gone. Acceptance: `tests/test_mir_leaf.py` byte identity green (op ids and digest bytes unchanged), a new drift test, census repin delta zero.

Stage B, one module per construct family: split `mirlower.py` (2710 lines) and `miremit.py` (1960) along the family boundaries the op comments already draw (scalar arith/compare, sequence, map, class/object, try callsite, call/builtin). A registry dict maps family name to lower/verify/print/emit hooks; a new family is a new file plus one sorted registry line, so parallel PRs own disjoint files. The dispatch if-chains in `miremit.py` (roughly lines 643-927) and `mirverify.py` become per-family hook calls. This is the largest stage and must land after Stage A so the registry, not the tables, is the shared surface.

Stage C, kill the editable lists: `tests/test_mir_leaf.py` `LEAF_SAMPLES` (lines 51-95) is a hand-maintained tuple that already drifted (the fixtures directory holds `leafnested.py` and `leafrt.py`, which are not in the list); replace with per-fixture discovery (`sorted(_FIXTURES.glob("leaf*.py"))` plus an explicit opt-out list only if a fixture must stay unparametrized). `tests/census_pins.json` is already sorted one-module-per-line (`scripts/repin_census.py` writes it that way "so PRs touching different modules merge without conflicts"), but 68 of the last 100 hotspot commits still touch it because every fence-lowering PR repins its own module; shard it into `tests/census_pins/<module>.json` files aggregated by the census test, or accept the single file but enforce that repins only change the author's module lines. `data/compat/support.json` is generated by `scripts/gen_support_table.py` (898 lines, `--check` mode exists); make CI run `--check` and stop hand-merging it, or shard by section.

Stage D, merge tooling and ordering rules: keep `scripts/repin_census.py` as the only repin path (the parallel session rules already say "census repin only via scripts/repin_census.py"); add a `scripts/mir_repin.py` only if Stage A changes what must be regenerated. Merge-order rules to write into `AGENTS.md` or the plan: each parallel batch declares owned files in its PR body; op ids get reserved hundred-ranges per family in the Stage A spec (for example scalar 0-29 is full, sequence 30-39, class 40-49 after renumbering is NOT allowed because ids are baked into digests, so instead new families take fresh blocks above 53 and the spec records the owner); two PRs may not both append ops; generated artifacts (`support.json`, census shards, any Stage A generated file) are regenerated by their script, never hand-merged.

## 5. Staged plan to v0.9.0 (45-minute shippable sub-tasks for devin sessions)

Stage 0, this PR: the plan doc only. Acceptance: docs-only diff, ruff clean, milestone v0.9.0. No hotspot rules apply beyond not touching code.

Stage 1, op-spec single-sourcing (conflict reduction first, per owner direction): spike whether `mir.py` can export `op_arity`/`op_result_type`/`is_terminator`/`is_value_op` as functions the self-host lowerer accepts (run `uv run python -m benchmarks.compat2.census_self` before and after; `mir.py` must stay at 0 fences). Then convert `mirverify.py`, `miremit.py`, `mirprint.py` to call them and delete the duplicated tables. Files: `mir.py`, `mirverify.py`, `miremit.py`, `mirprint.py`, `mirlower.py` (if it duplicates any table), `tests/test_mir_ops_drift.py` (new). Acceptance: `uv run pytest tests/test_mir_leaf.py tests/test_mir_hashseed.py tests/test_mir_verify.py -q` green, `uv run python scripts/mir_coverage.py` unchanged at 32/33, census repin delta zero. Hotspot rules: this PR owns all five op files; no other MIR PR may be open against them while it lands.

Stage 2, fixture and pin de-hotspotting, parallel-safe with Stage 1 if file ownership is respected (it touches `tests/test_mir_leaf.py`, `tests/census_pins*`, `scripts/repin_census.py`, `scripts/gen_support_table.py`/CI, none of which Stage 1 needs except possibly the drift test file): per-fixture discovery in `test_mir_leaf.py`, census pin sharding decision implemented, `support.json --check` wired into CI if not already. Acceptance: `uv run pytest tests/test_mir_leaf.py tests/test_census_self.py -q` green, repin script round-trips. This is the stage that pays back immediately because 68 percent of recent hotspot commits touch `census_pins.json`.

Stage 3, family-module split of `mirlower.py` and `miremit.py` behind the registry, serialized after Stage 1 (it moves the code Stage 1 just unified). Split into `mirlower/` and `miremit/` packages or sibling modules per family, one PR per family batch, each owning its files plus its registry line. Acceptance per PR: byte identity green, `mir_coverage.py` non-decreasing, census delta zero or better.

Stage 4, fence-clearing batches ranked by section 2: closures/env cells (M-4 note) first, then list/dict value-type completion (M-2), then try-handler tails if any remain, then the typed coro port (R-2) as its own epic because it is XL and also a v0.10.0 deletion. Each batch is one construct family, lands through the Stage 3 registry, and clears census fences measured by `census_self` plus corpus fences measured by `mir_coverage.py`. These can run in parallel across families once Stage 3 lands, with the merge-order rules from Stage D.

Stage 5, flip receipt and the flip itself: run `scripts/runtime_ab.py`, `scripts/compat_mir_flip.py`, `scripts/mir_perf_ratio.py`, `mise run bench:baseline`, `scripts/repin_census.py`, `scripts/gen_support_table.py`; amend #937 per section 3; land `MIR_DEFAULT = True` plus the escape-hatch test inversion in one PR; release notes slots from `.agents/notes/2026-11-06-v090-release-notes-draft.md`. Serialize everything: only one session runs the flip receipt at a time because the scorer run takes hours.

Parallel-safe versus serialize, summary: Stages 1 and 2 parallel (disjoint files, declared ownership); Stage 3 serial after 1; Stage 4 families parallel after 3 with per-family file ownership and no shared generated files; Stage 5 strictly serial. The direct-lowerer unfences named in the gap map (`shift`, `sieve`, `advance`, `check`) are `lower/` work and can run in parallel with everything above since they touch neither `mir*.py` nor the census pins of MIR modules, but each still repins `census_pins.json` for its own module, which is exactly the Stage 2 shard motivation.

## 6. Risks and open questions for the owner (recommended defaults)

1. Can the self-host lowerer accept function-form op tables in `mir.py`, or must Stage A fall back to a generated checked file? Default: spike first (Stage 1 step 1); if census fences appear in `mir.py`, use the generated-file-plus-drift-test fallback, which is guaranteed self-host safe because it is plain literals.
2. Should op ids stay ints or become name-keyed? Default: keep ints. The digest format (`serialize()` emits numeric op ids) is a frozen-adjacent contract and M-5's `MIR_HASHES.json` proposal is not landed; renumbering or rekeying ops is a v0.10.0 decision, not a conflict fix.
3. Does the byte-identity gate through v0.9.0 (per #937 layered gate) block better codegen before the flip, given `label_id`/`hint` exist only for byte parity? Default: keep it; the flip retires whole-module equality anyway and per-function identity is the cheap guard until then. Revisit only if a codegen win is blocked.
4. Is `support.json` regenerated by CI nightly or committed per PR? Default: `--check` in CI plus regenerate on release receipts, matching how `gen_support_table.py` already documents itself; never hand-edit.
5. Who arbitrates opcode id reservation and batch file ownership once Stage D lands? Default: the plan doc's rules plus a line in `AGENTS.md`; no new tooling until two batches actually collide after Stage A.
6. Does the user-centered gate need a numeric fence-cleared threshold, or is "no regression plus reported gains" enough for a minor release? Default: require the census delta and compat-ledger non-regression as hard gates and leave the magnitude to the release receipt, since the milestone's other exit criteria (compute two-plane, 0 open issues) already force real user-visible work.
